# Original-game observation protocol

S3-002 is partially implemented. The maintained interface verifies an operator's local evidence files and compares two candidate records. No original-game run has been recorded, and no runtime fidelity claim follows from these checks. The user has the reference remake repository and no original Gold installation. The [Amazons demo inventory](amazons-demo-inventory.json) records inspected archive bytes separately; it is not an observation fixture or evidence for Gold behavior.

The public types and validation entrypoints are in [original-observation.ts](../../scripts/lib/original-observation.ts). The CLI is `bun run observations`. Schema version 1 rejects unknown fields. Keep original executables, content, saves, and captures in local ignored storage. Commit metadata only when the files' provenance and redistribution permission have been reviewed. A download URL, a checksum, or inclusion in the reference remake does not establish redistribution rights.

## Prepare one fixture

1. Identify the actual original distribution and edition. Hash the executable and every content file affecting the fixture with SHA-256. Record the displayed version from the application if available, otherwise use `null`. Do not infer Gold identity from a demo or the reference remake.
2. Create a saved initial state, or identify the exact scenario file and document how to initialize it. Hash that file separately. Record locale, speed, display settings, difficulty, player configuration and any other starting conditions in `settings`. For a randomly initialized map, retain a save taken before commands rather than assuming the map alone reproduces the state.
3. Write UTF-8 JSON matching `OriginalObservationFixture`: `schemaVersion`, a stable `id`, `build`, `initialState`, `settings`, a nonempty `procedure`, ordered `commands`, and nonempty unique `outcomeKeys`. Every file reference contains a portable relative `path` and lowercase SHA-256. Paths resolve beneath the explicit original root. Commands use contiguous sequence numbers starting at zero, integer `atMs` values, and exact instructions. The procedure must describe selection, coordinates, pause/loading boundaries, runtime/emulator configuration, and how each outcome is measured.
4. Run `bun run observations fingerprint fixture.json`. Retain both emitted hashes. The starting-condition fingerprint covers build identities, initial state and settings; the whole-fixture fingerprint also covers procedure, ordered inputs and expected outcomes. Changing either invalidates an old run journal.

## Record an execution

1. Start the identified executable in the recorded OS/runtime. Restore the exact starting state and settings. Define zero time after loading is complete, immediately before accepting fixture commands. Do not count loading time as simulation time.
2. Capture a PNG at time zero and at the final observation time. Capture intermediate PNGs when needed to establish the visible outcomes. Record actual capture dimensions, OS and runtime in `environment`. Record continuous PCM RIFF/WAVE audio from zero through the entire run. Use external recording tools supported by the host; this CLI does not launch the original executable, record input, take screenshots or record audio.
3. Perform the ordered inputs and record actual elapsed integer milliseconds. Record every expected outcome with its key, measurement time and scalar value. Use an explicit unit in the key or fixture procedure. Keep the capture files unchanged and hash their actual bytes.
4. Write `OriginalObservationRun` JSON with the two fixture fingerprints, a UTC `recordedAt` timestamp such as `2026-10-21T00:00:00.000Z`, elapsed `durationMs`, environment, commands, outcomes and captures. Capture roles are `initial`, `final`, `visual` and `audio`. Initial time must be zero, final time must equal duration, and audio must start at zero and cover duration. If the game, recorder or procedure is interrupted, retain the available record as `status: "interrupted"`. Never label missing media or unperformed commands as completed.
5. Run `bun run observations verify fixture.json run.json original-root evidence-root > verified-run.json`. Exit 0 means a complete candidate with matching bytes and supported media. Exit 2 means an explicitly interrupted candidate. Exit 1 means invalid metadata, missing files, checksum mismatch or malformed evidence. A completed journal missing required inputs, outcomes or media fails verification.

Supported captures are decoded PNGs and PCM WAVE files with 1 to 8 channels, 8/16/24/32-bit integer samples and 8,000 to 192,000 Hz sample rates. The verifier bounds metadata to 1 MiB, each original file to 512 MiB, each capture to 64 MiB, run duration to 24 hours, and images to 8,192 pixels per dimension and 16,777,216 pixels total. The published PNG decoder separately bounds inflated scanlines and decoded buffers to 64 MiB, including intermediate 16-bit RGBA storage. It checks real paths against the chosen roots, rejects escaping symlinks, streams hashes, and validates the same bytes it decodes. These checks protect the evidence interface; they do not identify the contents as an original game or prove that capture timestamps are truthful.

## Repeat independently

Restore the same original bytes and initial state in a fresh execution. Follow the same procedure and retain a new timestamped journal and new captures. A second operator should review the executable provenance, reproduction steps and actual recordings. Comparing the same journal twice is rejected; changing its timestamp alone does not establish an independent execution.

Run `bun run observations compare fixture.json first.json second.json original-root first-evidence second-evidence [tolerance-ms]`. Both records are reverified against their local files before comparison. The default timing tolerance is zero; an explicit tolerance from 0 to 60,000 ms is retained in the report. A mismatch returns exit 2 with the first differing category, actual timing deltas and differing outcome keys. The report distinguishes changed starting conditions, procedure, incomplete runs, environment, outcomes, timing and media. Media comparison is exact SHA-256 equality, not a perceptual fidelity metric. Harmless recording differences can therefore report different media.

The reports always retain `originalBehaviorAdmitted: false`. Comparison also retains `independentExecutionVerified: false`, even for `matching-candidates`. Successful verification establishes metadata and byte consistency. Admission into an authoritative versioned rules catalog requires reviewed original provenance and independently repeated execution evidence. The test suite uses explicitly synthetic files and captures and cannot supply that missing evidence.
